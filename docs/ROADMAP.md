# 포트폴리오 개선 로드맵

처음부터 모든 기술을 넣기보다 **문제 재현 → 기준선 측정 → 선택지 비교 → 개선 → 회귀 검증**을 남긴다.
아래의 미래 단계는 계획이며 구현·측정했다고 주장하지 않는다.

| 단계 | 구현·개선 주제 | 포트폴리오에 남길 근거 |
| --- | --- | --- |
| 1. 현재 MVP | JPA + QueryDSL, 모듈 경계, 인증, 양방향 경매, 로컬 트랜잭션, PostgreSQL 행 잠금 | ADR, API 시연, 동시성·롤백 테스트 |
| 2. 측정과 조회 개선 | 부하 발생기, 입찰 대기와 p95/p99, 검색 실행 계획, 인덱스·키셋 페이징 | 동일 데이터·동일 자원의 전후 결과 |
| 3. 실시간 알림 | WebSocket/SSE, 재연결·누락 복구, 커밋 이후 전송 | 지연·재접속 시나리오, 중복·누락 테스트 |
| 4. 이벤트 신뢰성 | Transactional Outbox, 발행 재시도, 멱등 소비, 장애 주입 | 커밋 직후 장애·중복 메시지에도 주문/알림 보존 |
| 5. 선택적 MSA | 알림 서비스 우선 분리, 서비스별 데이터 소유권·배포·관측 | 분리 전후 장애 영향·운영비·지연 비교 |
| 6. 제품 확장 | 결제·배송·환불, React Native, 관심 목록·시세·검색 엔진 | 사용자 흐름과 실제 필요성에 근거한 선택 |

## 2단계: 먼저 측정할 질문

1. 같은 경매에 입찰이 몰릴 때와 서로 다른 경매에 분산될 때 처리량이 얼마나 다른가?
2. 행 잠금 대기, DB 커넥션 풀 대기, 쿼리 실행 중 어느 구간이 병목인가?
3. 낙관적 락으로 바꾸면 충돌률과 재시도 비용은 어떻게 변하는가?
4. 조건부 UPDATE를 사용하면 정합성을 유지하면서 왕복 횟수를 줄일 수 있는가?
5. QueryDSL 검색의 count와 깊은 offset에 어느 인덱스가 실제로 도움이 되는가?

조건을 고정한다: DB 버전, CPU/메모리, 풀 크기, 경매 수, 입찰 분포, 테스트 시간, 워밍업, 실패 분류.
정합성 테스트의 “16개 동시 요청 성공”을 성능 벤치마크로 소개하지 않는다.
실패 응답을 모두 서버 장애로 합산하지 말고 낮은 입찰가(409), 기한 종료(409), 실제 서버 오류(5xx)를 나눈다.

## Redis 도입 기준

우선 재생성 가능한 조회 캐시부터 검토한다. Redis 최고가만 갱신하고 DB 입찰 저장을 나중에 하는 변경은
유실·순서·재시작 복구 정책 없이 적용하지 않는다. 분산 락을 추가하는 것만으로 정합성이 해결되지는 않는다.

## Kafka/Outbox 도입 기준

낙찰 이벤트와 Outbox 행을 같은 DB 트랜잭션에 저장하고 별도 발행기가 전송한다.
발행 성공 표시 전 장애로 중복 전송될 수 있으므로 소비자가 이벤트 ID와 업무 유니크 키로 중복을 막아야 한다.
한 경매의 순서, 실패 메시지 재처리, DLQ, 운영 추적까지 함께 설계한다.
주문을 분리하면 현재의 즉시 일관성이 달라지므로 `낙찰 → 주문 준비 중 → 주문 생성` 상태를 모델링한다.

## 개선 기록 템플릿

```text
문제: 어떤 요청/부하/장애에서 문제가 발생했는가?
기준선: 환경, 재현 방법, 측정치, 실패율
가설: 원인이 무엇이라고 보는가?
대안: 각 선택의 정합성·복잡성·운영 비용
변경: 실제 바꾼 지점과 바꾸지 않은 조건
검증: 동일 조건의 전후 비교와 회귀 테스트
한계: 효과가 없는 조건과 다음 판단 기준
```

이 단계들을 Git 커밋이나 브랜치로 자동 생성하지 않았다. 사용자가 검토한 실제 변경 단위로 이력을 남긴다.
